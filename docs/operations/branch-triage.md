# Branch triage

How to decide, for every branch in this repository, whether it still carries
work `main` does not have — and what deleting it costs. The method is in
§1–§3. The result of running it on 2026-09-09 is in §4–§7, including the
delete lists, so the next pass does not have to redo the analysis.

**Headline: 143 of 144 local branches were already landed.** Exactly one
carries unmerged work. Deleting the rest removes 99 % of the branch list.

---

## 1. Why this needs a procedure at all

Two facts about this repository make branch state unreadable by eye.

**Direct-to-main with squash PRs.** Work lands through `gh pr merge --squash`
or a rebase. Both re-author the commit, so the branch tip is *not* an
ancestor of `main`, no patch id matches, and every file reads as changed. A
landed branch and a forgotten one are the same shape.

**Branches are hundreds of commits behind.** The median branch in the
2026-09-09 pass was 400 commits behind. At that distance a branch's tree is
mostly *older* than `main` everywhere, not just where it worked.

Together those produce the failure `scripts/dev/branch-status.sh` was written
for (2026-09-08): `git diff --stat main...branch` showed a tidy
`+10/−18`, because three dots is the MERGE-BASE diff and hides everything
`main` gained after the fork. The two-dot diff showed the same branch would
delete 158 files `main` had.

They also produce the quieter failure: **ancestry alone under-reports
landing by an order of magnitude.** On 2026-09-09 the ancestor test called 11
branches landed. The real figure was 143.

---

## 2. The four tests, strongest first

Apply them in order and stop at the first that fires. Each is exact except
the last.

| # | Test | Command | Proves |
|---|---|---|---|
| 1 | **Ancestry** | `git merge-base --is-ancestor <b> main` | The tip is literally in `main`. `git branch -d` accepts it. |
| 2 | **Tree identity** | `git rev-parse <b>^{tree}` appears in `git log --format=%T main` | The branch tip's whole tree is some commit on `main`, byte for byte. A squash landed it whole. |
| 3 | **Patch id** | `git cherry main <b>` shows no `+` | Every commit has an equivalent in `main`. Survives a rebase or cherry-pick. |
| 4 | **Content presence** | every line the branch ADDED appears somewhere in `main`'s tree | Heuristic. Strong evidence, not proof. |

Tests 1 and 3 are built into `make branch-status`. Tests 2 and 4 are manual;
§3 gives the recipes.

**What none of them catches: a squash of SEVERAL commits.** One squashed
commit has one patch id and it equals none of the originals, and its tree is
`main`'s, not the branch's. This is the repository's usual landing route, so
expect tests 1–3 to miss most of the pile — 92 of the 143 landed branches in
the 2026-09-09 pass. Settle those with test 4 plus §3's by-hand check.

### The trap in test 4

A line the branch added, that landed, and that `main` then edited again, will
not be found. So a ratio below 1.0 does **not** mean unlanded. Read the ratio
as a triage sort, never a verdict:

- **≥ 0.95** — residue is CHANGELOG churn, doc rewording and test-helper
  drift. Eight branches in this band were independently hand-verified in the
  2026-09-09 pass; all eight were landed.
- **< 0.95** — hand-verify. Do not guess.

Two artefacts dominate the false signal and should be excluded before
judging any branch: `examples/postman/stellar-index.postman_collection.json`
(regenerated by `scripts/dev/docs-postman.sh`) and `CHANGELOG.md`.

## 3. Running a pass

```sh
# 1. The tool. Judges by ancestry + patch id; exits 3 if any branch would
#    delete files main has.
make branch-status
BRANCH_STATUS_ARGS='--stale-only' make branch-status   # hide what has landed

# 2. Tree identity (test 2), over every branch at once.
git log --format='%T %h %s' main > /tmp/main-trees
git for-each-ref --format='%(refname:short)' refs/heads/ | grep -v '^worktree-' |
  while read -r b; do
    t=$(git rev-parse "$b^{tree}")
    hit=$(grep -m1 "^$t " /tmp/main-trees) && echo "$b  LANDED WHOLE as ${hit#* }"
  done

# 3. For anything still unresolved, find the squash that carried it.
git log --oneline main --grep='<issue number>'
git log --oneline main --grep='<a distinctive phrase from the branch subject>'
git log -S '<a symbol or string the branch introduced>' main -- <path>

# 4. Then prove the branch adds nothing main lacks. An EMPTY diff here is
#    the strongest single answer available:
git diff --stat <branch> <the-main-commit-you-found>
```

`git branch -d` refuses anything test 1 did not accept, so branches settled
by tests 2–4 need `-D`. That is expected, not a warning sign — but it does
mean git will not second-guess the delete, so the evidence must be recorded
before it is run. That is what §5 is.

**Ignore `worktree-*`.** Those are agent scratch from
`scripts/dev/bootstrap-worktree.sh`; `branch-status.sh` already filters them.
41 of the 186 local refs on 2026-09-09 were these.

## 4. The 2026-09-09 pass — result

186 local refs: 41 `worktree-*`, `main`, and **144 branches in scope**.

| Bucket | Count | Action |
|---|---|---|
| **1 — LANDED** | **143** | Delete. §5 has the commands. |
| **2 — carries work** | **1** | `fix/legal-pages-draft`. §6. |
| **3 — would delete files `main` has** | **93** | Never merge or cherry-pick wholesale. §7. |

Buckets 1 and 3 overlap by design: a landed branch that is 400 commits behind
would of course delete files, which is exactly why the answer is `git branch
-D` and never `git merge`.

Evidence behind the 143:

| Settled by | Count |
|---|---|
| Ancestry (test 1) | 11 |
| Tree identical to a `main` commit (test 2) | 38 |
| Every commit patch-equivalent (test 3) | 20 |
| Content present in `main`, ratio ≥ 0.95 (test 4) | 45 |
| Hand-verified against the squash that carried it | 29 |

The 29 hand-verified are the whole of the `< 0.95` band — none was resolved
by inference. Every one was traced to a specific `main` commit.

**93 of 144.** This is not a property of a few bad branches; it is what any
branch hundreds of commits behind looks like under a two-dot diff. The worst
are simply the oldest:

`make branch-status` prints the live list and exits 3 while any remain.

**92 of the 93 are already landed** (§5.2), so the correct action is
`git branch -D`, never a merge or a wholesale cherry-pick. **Exactly one
branch both carries work and would delete files: `fix/legal-pages-draft`
(577 files).** Take its three new page files, or rebase it — and prefer
`origin`'s copy, which is 280 commits fresher.

If a future pass finds a branch that genuinely must be applied: rebase it, or
cherry-pick individual commits after reading each one's
`git show --name-status <sha>`. Never `git merge` a branch this far behind.

## 8. Keeping the pile small

The mechanical backstop already exists: `.github/workflows/orphan-branches.yml`
runs daily, lists every **remote** branch with no open-or-merged PR whose last
commit is over 24 h old, and maintains one tracking issue. It does not see
local branches, which is where all 144 of these were.

The contract it enforces is
[CONTRIBUTING.md — No orphan work](../../CONTRIBUTING.md#no-orphan-work--the-contract):
push and PR are one step. The 2026-09-09 pile is what accumulates on the
*local* side of that contract — every one of those 143 branches did land, but
none was deleted afterwards. Deleting the branch is the last step of merging
it.
