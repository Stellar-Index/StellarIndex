## Read this before reading the numbers

Four things this measurement is not, each of which would otherwise be
assumed from the shape of the document:

1. **It is not a load test.** The probe drives 1 concurrent worker(s)
   in ~30 s bursts every 15 minutes; it measures served latency under
   whatever real traffic the host had at the time. ADR-0009 states
   p95 ≤ 200 ms and p99 ≤ 500 ms **unconditionally** — the target is not
   qualified by a request rate — so a low-concurrency measurement does
   test the stated target. What it does **not** exercise is ADR-0009's
   *enforcement* clause, which calls for a load test at volume. Nothing
   here is evidence about behaviour under concurrency the probe never
   applied.
2. **The probe measures `http://localhost:3000/v1` from inside the box.** Its requests never
   traverse DNS, TLS, the reverse proxy or any CDN, so the numbers
   below EXCLUDE every component ADR-0009's budget allocates outside
   the API process — 5 ms of TLS terminate + proxy ingress and 15 ms of
   network egress in the p95 table alone. **A client's p95 is strictly
   larger than every latency figure in this report.**
3. **Percentiles were not averaged, because percentiles do not average.**
   The probe exports one p50/p95/p99 per run and never the underlying
   samples, so the request-level population percentile for this window is
   not recoverable and is not computed here. The headline column is the
   **largest per-run percentile in the window**, which is a true upper
   bound on the pooled one: every run has ≥ 95 % of its samples at or
   below its own p95, so pooling runs keeps ≥ 95 % at or below the largest
   of those values, for any run sizes. The bound runs one way — under the
   target it PROVES the target held; over the target it proves only that
   this bound cannot settle it.
4. **Nothing is rolled up across endpoints.** There is no "overall p95"
   in this document. The verdict is the conjunction of the per-endpoint
   bounds, not a percentile of a merged population.

The two latency columns are **bounds**; the availability column is an
**estimate**, and they are different kinds of number on purpose. A
percentile cannot be pooled across runs, so the largest per-run value is
published instead and is a true ceiling on the pooled one. Availability
is a ratio and the SLO is a ratio over the window, so gating it on the
worst single 30-second run would fail a window the SLO was met in — each
run is weighted by the time its result stood instead, not by its request
count, which an outage or a hang collapses. `worst run` is kept
beside it because a window ratio hides a short total outage, and the
`window below target` column further down says how much of the week that
was.

Sample size: **1169 per endpoint per run** on average (min 1, max 4044 over
the window), across at least **632 recorded passing runs** — on the order of
**7,389,329 requests across all 10 endpoints** over 6d 23h. That is a real n, and it
is also 7,389,329 requests issued by one process from one vantage point, which is
not the same evidence as the same count spread across real clients. Run
sizes are not uniform, which is why nothing here is a simple average of
per-run values.

### Freshness — reported, not gated

Only endpoints that return an `observed_at` carry this series.
`/price` serves the ADR-0015 closed bucket and is structurally 30–150 s
old by design; the 30 s pricing SLA is served and measured on
`/price/tip`.

These rows carry no verdict, and that is deliberate. The deployed
freshness bound is enforced by `stellarindex_sla_probe_freshness_breach`
in `deploy/monitoring/rules/sla-probe.yml`, which requires the breach to
be **sustained for 30 minutes** — because a single run over bound is
in-contract: `computeTip` escalates its window and falls back to the
closed bucket, so a pair with no recent trade legitimately serves a
60–120 s `observed_at` (ADR-0018). Gating a worst-single-run value
against a threshold the live alert deliberately does not gate that way

## What this report does and does not prove

- It proves a **bound**, not a value. Where a row reads PROVEN the
  pooled percentile for that endpoint over this window cannot have
  exceeded the target. Where it reads NOT PROVEN the pooled percentile
  may still have been inside the target — the bound simply cannot settle
  it, and the per-run breach that produced it is named in the
  `window over target` column above.
- It excludes the **edge**. DNS, TLS terminate, the reverse proxy and
  any CDN are outside the measured path entirely. ADR-0009 defines its
  budget as edge-to-client and allocates 5 ms + 15 ms to exactly those
  hops, so a client-observed p95 is strictly larger than every figure
  here and this report does not evidence the end-to-end claim.
- It says nothing about **behaviour under load**. `test/load/scenarios/`
  holds the k6 scenarios that would, including the canonical 300 rps ×
  10 min soak; they compile on every PR and are one `workflow_dispatch`
  away from running, and they have no production-shaped target to run
  against. See docs/operations/sla-proof-procedure.md.
- It gates every endpoint at the headline 200 / 500 ms. ADR-0009's
  per-endpoint table is **tighter** for `/healthz`, `/readyz` and
  `/version` (p95 ≤ 5 ms, p99 ≤ 20 ms) and states no budget at all for
  `/assets`, `/issuers`, `/markets`, `/diagnostics/cursors` or
  `/price/tip`. A PROVEN row for a smoke endpoint here is therefore not
  a test of its tighter budget.
- The availability figure is the probe's own 2xx rate over its own
  requests. It is not an uptime SLO: a window in which the probe was
  the only client is not a window in which users were served.
- It is evidence about the build named in Provenance on the host named
  there. It does not transfer to a differently-shaped deployment.
