# 2026-08-22 — /v1/price p95 tail after the 0147 re-materialization

**RESOLVED 2026-08-24 — and the root cause below was WRONG.** The
re-chunk to 7-day materialization chunks was applied (a correct
hygiene fix in its own right) and the tail did NOT move — falsifying
the hot-chunk-churn theory. The real cause, proven from the slow-query
log (`duration: 324.586 ms  bind stmtcache_… SELECT … FROM trades`)
plus live PREPARE/EXECUTE measurement: the request path's raw-trades
fallback (TradesInRange) is a parameterised hypertable query that
Postgres flips to a GENERIC plan after five executions; building that
plan across the ~870-chunk trades hypertable costs ~206 ms, and the
plancache invalidates ~once a minute (autovacuum/analyze, compression,
chunk DDL), so a steady ~5 % of serving binds paid the rebuild. Custom
plans bind in 0.2–3 ms. Fix: the serving pool forces
`plan_cache_mode = force_custom_plan` post-connect (v0.40.1;
internal/storage/timescale/serving.go — background/ops pools keep the
default). Kept below for the elimination record and the follow-ups.

**Status (original, superseded): characterized, partially mitigated, monitoring.** The
`stellarindex_sla_probe_p95_breach` + `..._unit_failed_alert` pair firing
since ~2026-08-22 midday share one cause: the probe's `price` endpoint
(`native/fiat:USD`, sequential, 30 s window) reads p95 ≈ 250–330 ms
against a 200 ms target. p50 is pristine (12–15 ms); availability is
unaffected.

## What was proven / disproven

- The tail is **price-path-specific** (healthz stays sub-ms through every
  price spike) and **bursty** (0.5–7 % of requests, in clusters; one
  observed 17 s window where every request was slow).
- **Not** redis (SLOWLOG empty, latency monitor silent, BGSAVE sub-second),
  **not** the PG pool (14 idle under probe load), **not** plans/stats
  (closed-bucket read = 7 buffer hits; ANALYZE run on all 9 new
  materialization hypertables), **not** chunk bloat (14 k dead / 14.5 M
  live), **not** the CAGG policy refresh itself (17 ms/run), **not** the
  W-determinism `ORDER BY` tiebreak (Incremental Sort adds ~0.04 ms),
  **not** traffic growth (request rate flat-to-down), and **not a binary
  regression** — an A/B of the v0.39.0 API against the same live DB showed
  the same tail (5/60 vs 2/60 slow at small N).
- **Environmental root cause found:** migration 0147's CAGG recreate reset
  the materialization hypertables' `chunk_time_interval` to the ~70-day
  default — 28 chunks where the old layout had 382. The hot `prices_1m`
  chunk spans Jul-16→Sep-24, holds 14.5 M rows, and is rewritten every
  30 s by the refresh policy; reads intermittently stall on it. (The
  pre-0147 probe history is partially untrustworthy: a legacy
  RatesEngine-era `sla-probe.service` was interleaving writes to the same
  textfile until it was removed 2026-08-22 — so the exact onset time
  cannot be pinned.)

## Mitigation applied (2026-08-22)

`set_chunk_time_interval(<mat-hypertable>, INTERVAL '7 days')` on all
nine price/twap materialization hypertables — future chunks return to the
old ~7-day layout. Existing chunks cannot be split, so the current hot
mega-chunk keeps its churn until its range ends (**2026-09-24** for
prices_1m), after which new 7-day chunks take over.

## Follow-ups

1. If the p95 breach must clear before Sep-24: either re-materialize
   prices_1m once more (now chunked at 7 d — determinism makes this
   reproducible), or accept the alert with this note as the reference.
2. Any future CAGG-recreate migration must **capture and restore
   `chunk_time_interval`** exactly like 0115/0147 capture
   `materialized_only` (lesson recorded in the audit-suite backlog).
3. Enabling pprof on the API metrics listener would make the next tail
   investigation a 10-minute profile instead of an evening of
   elimination.
4. Pre-existing, unrelated, worth a look: `oracle_prices_1m` carries a
   ~447 k-entry materialization-invalidation-log backlog.
